# P10B-01 — Storefront Design System capability and visual-quality audit

**Audit date:** 5 August 2026

**Repository baseline reviewed:** `codex/p10b-01-storefront-design-system-capability-audit` (from `origin/main`)

**Scope:** documentation and repository evidence only. No provider call, runtime code, PageBlueprint, SDD, DOCX, baseline, or fixture was changed.

**Current authority:** This pre-implementation audit remains historical evidence. Its provisional
delivery implications are superseded by
[`P10B_COMMERCIAL_STOREFRONT_GENERATION_ARCHITECTURE.md`](P10B_COMMERCIAL_STOREFRONT_GENERATION_ARCHITECTURE.md);
its factual findings are unchanged.

## 1. Executive conclusion

The repository has the beginnings of a controlled storefront design system, not yet a commercially complete one. Its important strengths are real: one canonical `StorefrontSnapshot`; registered components and variants; bounded presentation values; protected commerce and approved-asset rules; three coordinated directions; and the same registered implementations across editor, preview and published targets where the V2 bridge is active. Those foundations should be extended, not replaced.

The visual ceiling is nevertheless **a competent, clean, responsive catalogue storefront with limited brand distinction**, rather than the “commercially credible, differentiated AI outcome” intended by the SDD. The main cause is not a lack of names in the registry. It is that composition and presentation authority is thin at the points that make a store recognisable:

- the three executable PageBlueprint profile families retain mostly the same legacy collection/PDP composite-slot representations, even though the whole-storefront runtime correctly replaces them with native dynamic commerce instances;
- homepage has native V2 commercial section bridges, while the whole-storefront runtime already materializes `dynamicCollectionCommerce` and `dynamicProductDetail` as canonical collection/PDP replacements; the remaining gap is the narrow visual range of their governed profiles;
- the `BrandSystem` governs a small semantic palette, four font tokens, one density, one radius, and a few visual-system enums, but does not govern a usable type scale, spacing scale, surface/elevation scale, layout grid, image focal-point/crop, or per-component token mapping;
- many registered variants are CSS-class substitutions over the same DOM and composition, and some V2-declared variants are not selected by the executable profile set;
- media treatment is limited to `object-fit`, a few fixed aspect ratios and a single hero overlay. Asset contracts preserve provenance and role very well, but do not yet carry art direction that materially changes responsive images;
- directions coordinate headline choices on the homepage, but collection and PDP page plans remain materially similar. They therefore risk converging after the first viewport and especially in commerce-heavy flows.

This is a bounded design-system implementation opportunity, not permission for free-form generation. Storefront Design System v1 should make existing canonical authority more expressive: `BrandSystem → registered PageBlueprint profile → compatible family/variant → validated instance`. It must not introduce another token store, direction registry, recipe engine, page tree, or renderer path.

## 3. Audit method and evidence boundary

The audit traced the live path below and treated repository contracts as authoritative over older report prose:

```text
whole-storefront planner
  -> registered template/PageBlueprint profile
  -> ComponentDefinitionV2 and legacy/Puck bridge
  -> validated StorefrontSnapshot
  -> shared editor / preview / published renderer
```

Primary evidence was read in:

- `src/application/whole-storefront-generation-plan/planner.ts` (direction-to-template mapping);
- `src/application/storefront-templates/{contract,registry,materializer}.ts` (executable profile and slot authority);
- `src/components/registry/{v2-registry,homepage-commerce,dynamic-collection-commerce,dynamic-product-detail,design-vocabulary}.ts` (current registered capability);
- `src/application/storefront-design-system/registry.ts` and `src/domain/design-system/brand-system.ts` (direction and brand-token contracts);
- `src/components/storefront/*` CSS/React renderers (what becomes visible);
- `src/domain/shared/asset-role.ts` and asset-conformance paths (asset governance);
- `src/data/seed/aurum-nordic.ts`, P9/P10A tests and review documents (fixture and quality evidence).

The SDD requires professionally distinct variants, constrained profile composition and human screenshot review (FR-109, FR-114, FR-119–122; AC-134, AC-136–137; NFR-103). This audit does not claim that fixture-pass evidence is equivalent to a commercial review.

## 10. Brand and asset-treatment audit

`BrandSystem` is the correct canonical global authority. It owns palette, typography, shape, density, imagery style, voice, optional visual-system values and semantic presentation colours; it derives CSS custom properties and contrast-safe action foregrounds. This is a valuable safety and inheritance base.

However, it currently cannot describe a full visual language. `visualSystem` has content width, surface/divider/button/image/theme enums and optional border/depth/aspect/crop fields, but component CSS does not consistently consume a semantic scale created from them. Direction packages repeat similar concepts in a second registry (`typographyDirectionId`, `imageTreatmentId`, `spacingDensity`, `cornerTreatment`, `surfaceDepth`, recipe IDs and selected components). That registry is valid only as a registered direction projection; it must not become a parallel token authority.

Asset governance is stronger than treatment governance:

- asset roles are explicit (`logo`, hero desktop/mobile, collection, product main/alternative, editorial, supporting, icon);
- V2 slots declare accepted roles and cardinality;
- approved placement records preserve asset identity, role, revision, provenance and material fingerprint;
- product and collection renderers fail closed for invalid canonical/approved media.

The missing authority is design use: role-to-aspect-ratio, focal point, responsive crop derivative, overlay-safe area, background/surface pairing, decorative policy, priority/loading and permitted component treatments. The correct next step is to extend the canonical asset/presentation contract and renderer projections, not to copy image metadata into section content or create a second asset inventory.

## 12. Highest-impact visual gaps

1. **One canonical product-card system is missing.** Three overlapping product-card authorities prevent consistent card anatomy, density, media, badges and responsive behaviour across home, collection and related products.
2. **Collection/PDP profile diversity is insufficient.** The richer native dynamic commerce renderers already materialize through the canonical generation, proposal and stored-runtime path, but current directions exercise too few governed combinations of discovery, density, gallery, purchase, proof, service and related-product composition.
3. **Typography is a font-pair setting, not a type system.** Component-local `clamp()` declarations overwhelm the small global scale contract.
4. **Image treatment has provenance but no art direction.** Without focal point/crop/ratio/overlay/pairing authority, distinct briefs reuse the same generic image patterns.
5. **Shared-frame depth is too low.** Header/footer/nav options do not provide the credibility cues of a premium, editorial, technical or friendly retail frame.
6. **Editorial/campaign storytelling is shallow.** Existing modules are largely variations of image/text blocks, leaving no controlled way to create a coherent brand narrative.
7. **Direction differentiation is not sufficiently deep beyond the homepage.** Collection/PDP runtime variants already materialize, but composition, promotional intensity, navigation and information density need richer registered cross-page coordination.
8. **Visual proof is incomplete.** Deterministic geometry and fixture diversity gates should remain, but actual screenshot review and documented scored judgement are required before claiming commercial quality.

## 13. Proposed Storefront Design System v1 architecture

The v1 architecture should retain the existing authority chain:

```text
BrandSystem (expanded semantic foundations)
  -> registered PageBlueprint profile (page recipe and cross-page rules)
    -> ComponentDefinitionV2 family / meaningful variant
      -> validated bounded instance values
        -> existing shared editor, preview and published renderer
```

### 13.1 Canonical extensions

| Authority to extend                 | Add, bounded by schema                                                                                                                                                                       | Must not add                                                                          |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `BrandSystem`                       | Semantic type roles/scale, spacing scale, surface/elevation/border grammar, layout/container/density roles, tokenised control states and image-treatment defaults.                           | Font URL/free-form CSS, arbitrary colours, a second token store, per-page raw values. |
| Asset metadata / approved placement | Role-compatible aspect ratio, focal point/safe area, permitted crop/treatment, responsive derivative references and priority/decorative rules.                                               | A second asset inventory, editable product media, unapproved image generation path.   |
| `ComponentDefinitionV2`             | Family-specific variant semantics, component token consumption, visual/asset compatibility, intentional responsive states and non-overlapping product-card contracts.                        | Merchant-specific components, raw CSS or renderer-specific authority in planner data. |
| `PageBlueprint` profile             | Required/optional commercial roles, bounded section count/order/weight, direction-compatible pages, composition parameters, content/asset omissions and cross-page density/navigation rules. | Another recipe/page graph, an independently persisted plan or direct renderer trees.  |
| Registered direction package        | References to the above canonical values and a coherent home/collection/PDP/frame package.                                                                                                   | A duplicated design-system recipe/token model.                                        |

### 13.2 Design foundations to govern

- **Type:** `display`, `h1`, `h2`, `h3`, `body`, `bodySmall`, `label`, `price`, `eyebrow`, `button`; each derives from the approved font, scale and weight constraints.
- **Space/layout:** named page gutters, content/readable/commerce widths, section rhythm, grid gap, card padding, control height and density rules. Renderers consume them rather than hard-coded unrelated clamps.
- **Surface:** background, section, raised, inset, inverse, border, focus and status roles; bounded elevation and radius grammar.
- **Media:** semantic ratio/crop/overlay/text-safe-area tokens resolved only for compatible asset roles and components.
- **Responsive:** each family explicitly declares the state at 375, 768, 1024 and 1440 (not only “no overflow”); the profile coordinates density, order, media crop and navigation mode.

## 15. Commercial-quality acceptance rubric

Use this review for each generated storefront direction, across shared frame, homepage, one collection and one PDP at 375, 768, 1024 and 1440 px in EN and FI. A reviewer marks each criterion **pass**, **needs correction**, or **blocked**, adds an evidence reference and a concise reason. A pass requires no unresolved blocker and retained evidence tied to the snapshot/profile/renderer fingerprint.

| Criterion                      | Pass condition                                                                                                                                                                         | Deterministic supporting evidence                                                                   |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Brand distinctiveness          | The store has a recognisable coherent visual point of view beyond palette; pairwise directions visibly differ in at least typography, image treatment, frame, density and composition. | Registered direction/profile/variant and token fingerprints; pairwise non-colour difference checks. |
| Hierarchy and composition      | First screen, section sequence and calls to action communicate a clear commercial priority; no repetitive image/text cadence or adjacent competing dominant sections.                  | PageBlueprint narrative roles, visual-weight/flow validation, section order and human screenshots.  |
| Typography                     | Type roles are legible, consistently scaled and brand-appropriate; headings, price, labels and long Finnish strings remain distinct/readable.                                          | Token resolver output, contrast/overflow checks, EN/FI screenshot rows.                             |
| Imagery and art direction      | Images are approved, appropriately cropped, purposeful, accessible and support copy/merchandising; no generic or badly cropped hero/card media.                                        | Asset role/provenance/crop conformance plus screenshot review.                                      |
| Merchandising                  | Product cards reveal the right canonical media, price, state and meaningful comparison cues at a direction-appropriate density.                                                        | Protected commerce/card binding tests and product-count screenshots.                                |
| Collection discovery           | Navigation, featured collections, filters and result cards make browsing obvious and direction-appropriate.                                                                            | Binding/order/filter functional checks plus collection screenshots.                                 |
| PDP quality                    | Gallery, price, availability, options, specifications/proof and purchase action support confident selection; option/disabled states are understandable.                                | Dynamic option and protected-commerce tests; mobile/desktop screenshots.                            |
| Responsiveness                 | At each viewport there is no clipping/overlap and the chosen direction still has deliberate hierarchy, reachable controls and touch/keyboard usability.                                | Existing geometry/a11y test evidence plus screenshots.                                              |
| Cross-page consistency         | Frame, tokens, cards, image treatment and promotional intensity are coherent across home, collection and PDP without flattening the pages into clones.                                 | Direction/profile fingerprint correlation and all-surface screenshot review.                        |
| Visual repetition              | Repeated card/section patterns have deliberate variation; no unexplained dead space or mandatory generic filler.                                                                       | Section cardinality/repetition rules, content-count cases, screenshots.                             |
| Protected commerce correctness | Prices, SKU, availability, options, product/collection membership and canonical media remain correct and unedited by presentation.                                                     | Snapshot/projection/asset fingerprints and negative binding tests.                                  |

This rubric should be added to the existing human-commercial-review protocol rather than creating a competing review record. Deterministic checks supply necessary evidence; a trained human remains responsible for the visual judgement.
